# Locus Benchmarks

Reproducible benchmarks covering retrieval quality, signal contribution,
and indexing/query performance.

## Running

```bash
# Full run — 100-doc corpus, all benchmarks
python benchmarks/run.py

# Quick run — smaller corpus
python benchmarks/run.py --docs 50 --fast

# Latency profiling only
python benchmarks/run.py --latency-only

# With rank_bm25 baseline comparison
pip install rank_bm25
python benchmarks/run.py
```

Results are saved to `benchmarks/results/latest.json` and a timestamped file.

## Honest Interpretation

### What the synthetic corpus shows

The 100-doc synthetic benchmark uses templated documents with minimal
entity relationships. On this corpus:

- **BM25 alone performs as well as the full pipeline.** This is expected:
  the KG, link-walking, and link-popularity signals require genuine content
  interconnection that templated documents lack.
- **rank_bm25 matches Locus BM25** (0.590 vs 0.600 R@5). The minor gap
  is tokenisation differences, not algorithmic. Both are BM25 at the core.
- **grep is 7pp behind** on R@5, confirming IDF weighting adds real value
  even on simple corpora.

### What real corpora show

Locus's multi-signal architecture is designed for knowledge bases with:

- **Wikilinks between documents** — link-walking expands retrieval to
  contextually related chunks that share no BM25 terms with the query.
- **Named entities with relationships** — KG retrieval surfaces documents
  about the *entities in the query* even when exact terms don't match.
- **Frontmatter metadata (date, tags, type)** — structural retrieval
  handles temporal and categorical queries that BM25 misses completely.
- **Mixed freshness** — recency prior and link popularity distinguish
  current authoritative documents from stale ones.

On an interconnected Obsidian vault or engineering knowledge base, each
signal adds measurable recall. The synthetic corpus is intentionally the
*worst case* for Locus's multi-signal approach — and even here it stays
competitive with rank_bm25.

### Comparison with vector RAG

Locus is not trying to compete with embedding-based retrieval on semantic
similarity tasks. The tradeoff is explicit:

| Dimension | Locus | Vector RAG |
|---|---|---|
| Setup | `pip install locus-rag` + index | Embedding model + GPU/API |
| Dependencies | Zero (pure stdlib) | transformers / openai / etc. |
| Retrieval type | Keyword + graph + structure | Semantic similarity |
| Transparency | Per-chunk provenance tags | Black box scores |
| Temporal queries | Native (valid_from/valid_to) | Requires metadata filter |
| Explainability | `locus explain <chunk_id>` | Not available |
| Cost at scale | SQLite on local disk | API calls or GPU time |

The right tool depends on your corpus and constraints. Locus excels when
you want **zero infrastructure friction**, **full explainability**, and
**structured knowledge** (entities, dates, relationships) alongside
free-text retrieval.

## Benchmark Methodology

- **Corpus**: Synthetic markdown documents generated by `locus/bench/synthetic.py`.
  Each document covers a distinct technical topic (authentication, deployment,
  monitoring, etc.) with realistic structure: YAML frontmatter, headed sections,
  wikilinks, and named entities.
- **QA pairs**: Derived deterministically from document content — no human
  annotation required. Each document produces 2–3 queries using its primary terms.
- **Metrics**: Recall@K (fraction of queries where the correct document appears
  in the top-K results) and MRR (Mean Reciprocal Rank).
- **Latency**: Wall-clock time including SQLite I/O. Measured with
  `time.perf_counter()`, `use_cache=False` to avoid cache warm effects.
- **Environment**: Windows 11, Python 3.14, NVMe SSD, no GPU.
- **Reproducibility**: Fixed seed (42). Run `python benchmarks/run.py` to
  reproduce.
